# WASI Preview 3 CLI (experimental vertical slice)

The first WASI 0.3 integration uses the existing Process Worker per process,
Core supervisor, and direct MessagePort/OPFS stream endpoints. Native
Component Model async scheduling and `stream<u8>`/`future` are implemented
by the jsco component runtime, not emulated using P2 pollables.

## Implemented path

- A Component is recognized by its exported `wasi:cli/run@0.3.0` (or
  `@0.3.0-rc-2026-03-15`) world, since P2 and P3 use the same binary header.
  P1 Core modules and P2 commands keep their existing paths.
- P3 CLI `environment`, `exit`, `stdin`, `stdout`, `stderr`,
  `terminal-*`, `types`, `clocks`, and `random` imports are delegated
  to jsco's P3 Host. Arguments and environment are explicit process snapshots;
  missing child `PWD` is not supplied or validated at spawn.
- JS `ReadableStream`/`WritableStream` adapt the existing Worker-local
  byte streams. Each write honors the direct Pipe's 64 KiB capacity and
  16 KiB permits. EOF is delivered when the process closes its output.
- `wasi:cli/exit` and `exit-with-code` retain walos exit status reporting.
  The supervisor still handles stop requests and terminates unresponsive
  Workers. P3's own async work is not run in the Core Worker.

## Deliberate limits

**This is not complete WASI 0.3 conformance.** Unsupported P3 imports fail
during initialization, rather than silently bind to unrelated host facilities:

- P3 `wasi:filesystem/*` is **not yet connected to OPFS**. In particular,
  jsco's default in-memory filesystem is never used for walos programs.
- `wasi:http/*`, `wasi:sockets/*`, and `walos:runtime/*` P3
  extensions are not supported. A P3 component mixing P2 imports is rejected.
- Target versions are `0.3.0` and the
  `0.3.0-rc-2026-03-15` compatibility snapshot. Later 0.3.x interfaces,
  including the 0.3.1 map/annotation requirements, are not supported here.
- jsco `0.2.0-preview.0` is preview-quality. The underlying P3 Host and
  Canonical ABI implementation must be independently validated before
  claiming standards conformance.
- P3 guest binaries are **not** generated by the existing wasi-sdk 27 C
  fixture build. The included browser tests cover dispatcher selection and
  the real PortStream/Web Streams bridge, **not** a P3 Wasm binary executing.
  An end-to-end `wasi:cli/command@0.3.0` test fixture remains to be added.

## Running a P3 CLI binary

The public Host API is unchanged. Write a P3 command Component into OPFS
through a readable `FileDescriptor`, then call
`host.process.spawn(executable, argv, env, stdin?, stdout?, stderr?)`.
Explicit stream endpoints move on spawn; omitted ones use Null. As with
P1/P2, `child.wait()` is one-shot and dropping a child handle does not
terminate it.

To verify the included tests after `npm ci` and a full demo build:

```sh
npm run check
npx playwright test tests/wasip3.spec.ts
npm test
```

Planned next steps are an OPFS-backed P3 filesystem, a real P3 Wasm CLI
fixture with P1/P2/P3 cross-version Pipe tests, and validation against
WASI 0.3's published async Canonical ABI and test suite.
